# 自建服务器面板二开完整路线图（基于 Coolify fork）

## Context（背景与目标）

用户已在本机（WSL2 + Docker）成功部署 Coolify（fork 于 v4.5.1，代码在 `g:\xianmu\juqing\baoUIIT`），现在想把它二开成一个**面向中文站长/轻技术用户的服务器管理面板**——对标"宝塔的服务器管理体验 + Coolify 的部署自动化能力"，原生中英双语。用户自身就是目标用户（宝塔企业版功能用不起），动机真实。

**产品定位一句话**：中文原生的现代服务器面板——像宝塔一样简单管服务器，像 Coolify 一样一键部署应用（重点吃 AI 应用一键部署这个增量市场）。

**法律前提**：Coolify 是 GPL-3.0，二开分发必须继续开源、保留原版权声明、衍生作品同协议发布。

## 阶段 0：工程基建（第 1 周）

**目标**：可维护的 fork，不丢上游更新能力。

1. **建仓**：本地 Git 已存在 → 推到私有仓（Gitee 优先，国内拉取快；GitHub 同步镜像）。分支策略：`main`（发布）/ `next`（开发）/ `upstream-sync`（跟踪官方）。
2. **基准标签**：`git tag v4.5.1-base` 锁定 fork 基点，后续合并上游用 `git merge upstream/vX.Y.Z` + 冲突清单。
3. **改名不急于全局替换**：先只改用户可见处（登录页标题、邮件签名、favicon），代码内 `coolify` 命名空间不动——否则合并上游必炸。
4. **开发环境固化**：把本次 WSL2 部署过程写成 `docs/dev-setup.md`（仓库内），含 `.env` 模板、WSL 启动命令、常见问题。
5. **CI 底线**：GitHub/Gitee Actions 跑 `vendor/bin/pint --test` + `php artisan test --compact`（非 browser 部分）。

## 阶段 1：中英双语（第 2-4 周）

**原则**：先基建后批量，脚本半自动化，分优先级交付。

### 1.1 基建（1-2 天）

- 新建 `app/Http/Middleware/SetLocale.php`：优先级 `session('locale')` → `auth()->user()->locale` → `config('app.locale')`；`app()->setLocale($locale)`。
- 注册到 `app/Http/Kernel.php` web 组（在 `StartSession` 之后）。
- 迁移加 `users.locale` 字段（默认 `null`，参考 `add_current_team_id_to_users_table` 写法）。
- 语言切换 UI：侧边栏底部（`navbar.blade.php` 菜单区末尾）加中/英下拉，点击后写 session + user 字段，`$refresh`。
- `Profile/Appearance.php` 同款模式在 Profile 页加"语言"设置项（持久化）。

### 1.2 翻译工程（2-3 周，核心工作量）

- **写提取脚本** `scripts/extract-i18n.php`（一次性工具，放仓库 scripts/ 下）：
  - 扫描 blade 中的英文文本节点和 `title=/placeholder=/label=` 等属性；
  - 生成 dot 风格键（按视图路径前缀，如 `dashboard.no_projects`）；
  - 自动替换视图为 `__('dashboard.no_projects')` 并输出 `lang/en.json` 骨架 + `lang/zh-cn.json` 待译清单。
- **翻译批次**（按用户停留时长排序，每批交付即可用）：
  1. 侧边栏/导航/全局按钮（约 200 处）
  2. Dashboard + Projects 列表/详情（约 400 处）
  3. Application 部署全流程页面（约 500 处）
  4. Database/Service/Server 管理页（约 500 处）
  5. Settings/Profile/Notifications/Terminal（约 400 处）
  6. Livewire PHP 类中的 toast/确认/验证消息（约 1500 处，用脚本扫 `->dispatch('success', '...')` 等模式）
  7. 长尾页面
- **AI 初翻 + 人工校对**：脚本导出 CSV → 批量机翻 → 你过一遍关键页面。
- 验证：每批完成后 `php artisan test --compact` + 浏览器切语言走查截图。

## 阶段 2：差异化功能（第 5-10 周）

按"自用痛点 × 实现成本"排序，每个都是独立可交付的模块：

| # | 功能 | 技术路径 | 成本 |
|---|---|---|---|
| 2.1 | **AI 应用一键部署商店** ⭐ | 扩展 `templates/service-templates.json`，内置 20+ 中文模板：Dify、n8n、OpenWebUI、NewAPI、OneAPI、Uptime Kuma、WordPress、Halo 等；模板 slogan/tags/category 中文化；预填国内镜像源 | 低，最快见效，先做 |
| 2.2 | **国内通知渠道** | 现有 `app/Notifications/` 体系加企业微信/钉钉/Server酱 webhook 通道（部署成败、服务器告警） | 低 |
| 2.3 | **服务器监控仪表盘增强** | 复用 `HasMetrics` + `ServerMetricsChart`：补磁盘/网络/历史时间范围选择/多服务器总览页 | 中 |
| 2.4 | **应用文件备份计划** | 扩展 `VolumeBackupJob`/`ScheduledVolumeBackup`：支持定时备份应用目录+数据库，目标加 S3 兼容（七牛/阿里云 OSS/腾讯云 COS 走 S3 协议即可） | 中 |
| 2.5 | **在线文件管理器** | 复用 `TerminalSessionService` 的鉴权与 SSH 通道：列目录(ls)/读写(cat/tee)/上传下载(base64 分块)/压缩解压；前端 Livewire 组件 + Alpine 编辑器（monaco 太重就用 textarea+高亮） | 高，最后做 |

## 关键技术原则（全程遵守）

1. **只加不改**：优先新增模块（新组件/新路由/新视图），万不得已不改 Coolify 原有逻辑——保上游合并能力。
2. **每功能带测试**：参照 `tests/v4/Browser/` 写关键路径浏览器测试；bug 修复先写失败测试。
3. **提交纪律**：`vendor/bin/pint --dirty --format agent` 每次收尾；commit message 英文、说明 why。
4. **翻译即代码**：翻译文件进版本库，禁止"线上直接改"。
5. **安全底线**：遵循 AGENTS.md 授权规则——所有新页面必须走 policy 鉴权 + team 隔离，文件管理器路径严格限制在授权服务器/容器内，防路径穿越。

## 里程碑验收标准

- **M1（阶段1末）**：全中文界面下无英文裸漏完成一次 WordPress 部署。
- **M2（阶段2末）**：填域名 3 分钟部署 Dify；服务器掉线 5 分钟内企业微信收到告警；应用目录定时备份到 OSS 且可恢复。
- **M3（阶段3末）**：一台干净的 Linux 服务器，一条 curl 命令装完面板，默认中文，文档站可访问。

## 验证方式（每个阶段通用）

1. 本机环境验证：`wsl -d Ubuntu` → `/opt/coolify-src` 更新代码 → `docker compose restart`（或重新 build）→ 浏览器 `http://localhost:8000` 走查。
2. 自动化：`php artisan test --compact`（功能测试）+ `php artisan test --compact tests/v4/Browser/`（关键 UI 流程，截图核验）。
3. 干净环境验证：WSL 里另起一个 Ubuntu 实例或找一台 VPS 跑 `install.sh` 全流程。

## 主要风险与对策

| 风险 | 对策 |
|---|---|
| 5000+ 处翻译工作量失控 | 批次交付，前 4 批已覆盖 90% 使用场景，长尾允许英文残留 |
| 上游大版本合并冲突 | 阶段 0 的改动清单 + "只加不改"原则；每季度评估是否值得合并，不值得就锁定版本 |
| 一个人做不完 | 严格按优先级砍需求；"不做清单"写死后不回头 |
| 没人用 | 阶段 2.1 完成后就发内测帖，不等全部做完 |
